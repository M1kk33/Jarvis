# M12 screenshot setup

M12 answers a question about one PNG screenshot deliberately selected in the browser. The screenshot is previewed before sending. Sending saves it as a private, immutable conversation artifact under the selected `--data-dir`, and backups include it. The conversation displays the source image alongside the question and text answer. Jarvis has no screenshot deletion control in M12; remove private data only through a separately planned retention feature or by managing the whole data directory yourself. A crash or rejected concurrent submission before the transaction can leave an unreferenced staged screenshot under `artifacts/`; Jarvis never silently reuses it. No background capture, browser control, or UI action follows from the answer.

The worker uses the existing pinned [llama.cpp b11429](https://github.com/ggml-org/llama.cpp/releases/tag/b11429) binary and the [Qwen2.5-VL-3B-Instruct GGUF Q4_K_M with matching Q8_0 projector](https://huggingface.co/ggml-org/Qwen2.5-VL-3B-Instruct-GGUF/tree/5037fcf163dd95d1e41d1974465f0898ed108ca2). The model repository is Apache-2.0-licensed. Copy [the exact profile](../profiles/qwen25-vl-3b.example.toml) to `E:\JarvisData\vision.toml`; adjust only the local paths and GPU identity. The profile verifies all three file hashes, including the executable. Downloads are explicit setup actions; normal use stays offline.

```powershell
E:\JarvisData\runtimes\speech-base\Scripts\python.exe -c "from huggingface_hub import snapshot_download; snapshot_download(repo_id='ggml-org/Qwen2.5-VL-3B-Instruct-GGUF', revision='5037fcf163dd95d1e41d1974465f0898ed108ca2', local_dir=r'E:\JarvisData\models\qwen25-vl-3b', allow_patterns=['Qwen2.5-VL-3B-Instruct-Q4_K_M.gguf','mmproj-Qwen2.5-VL-3B-Instruct-Q8_0.gguf'])"
Copy-Item profiles\qwen25-vl-3b.example.toml E:\JarvisData\vision.toml
uv run --offline --locked --python 3.12 python -m jarvis --data-dir E:\JarvisData --profile E:\JarvisData\model.toml --vision-profile E:\JarvisData\vision.toml web
```

The download command uses the already installed M10 `huggingface_hub` environment on this PC; any trusted Hugging Face client can fetch the same pinned revision. The browser accepts one PNG at a time, up to 2 MiB and 1024 × 1024 pixels, with a question of at most 1,024 characters. The worker's image-token cap is 1,024 within a 4,096-token context; an exact multimodal token count must also fit before generation. Vision loads only after the text model exits and releases the GPU lock, then exits after answering. The provisional cold bound is 5.5 GiB VRAM and 6 GiB RAM plus the normal 1/3 GiB reserves. A failed admission leaves the question and screenshot visible as a failed turn, without inventing an answer.

On this PC, the fixed five-screen evaluation completed a text → vision → text handoff. Sampled system free VRAM fell from 6.929 to 3.679 GiB, and available RAM from 9.630 to 6.883 GiB, across the full run; both remained above reserve. These system-wide 250 ms samples can miss shorter spikes and include unrelated desktop activity. The vision model identified the clear Save/Retry controls and treated an obscured status code as unknown after its uncertainty instruction was strengthened. It described the injected warning as screenshot content without executing an action. This set is a basic fit and behavior check, not a promise of accurate small-text reading on arbitrary screenshots.

Screenshots may contain misleading or malicious instructions. Jarvis sends the image only as evidence to a model with no tool or approval channel. The answer may still misread small text; it should state uncertainty when exact details are not legible. M12's fixed UI evaluation runs through `JARVIS_TEXT_PROFILE` and `JARVIS_VISION_PROFILE` in `tests/test_m12_hardware.py`.
